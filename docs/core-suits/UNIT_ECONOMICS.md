## 1回の接客にかかる原価（実測値）

| 動作 | モデル | 実測 | 原価 |
|---|---|---|---|
| 試着 1枚 | gemini-3.1-flash-image | 入力 981 tok / 出力 1,404 tok / 12.2 秒 | **¥13.2** |
| 提案 3案 | claude-haiku-4-5 | 入力 590 tok / 出力 281 tok / 3.9 秒 | **¥0.31** |

典型的な1回の接客（試着3枚 + 提案2回）= **約 ¥40**。

## プラン別

| | Starter ¥9,800 | Pro ¥29,800 | Enterprise ¥98,000 |
|---|---|---|---|
| 試着上限 / 月 | 50 | 300 | 1,500 |
| **上限まで使った AI 原価** | **¥660** | **¥3,960** | **¥19,800** |
| 提案の原価（試着の2倍と仮定） | ¥31 | ¥186 | ¥930 |
| Supabase / Vercel（店舗あたり按分） | ¥200 | ¥400 | ¥1,500 |
| **原価合計（最悪ケース）** | **¥891** | **¥4,546** | **¥22,230** |
| **粗利率（最悪ケース）** | **91%** | **85%** | **77%** |

「最悪ケース」= 上限まで使い切った場合。実際の店舗は上限の 3〜6 割程度と見込んでいるので、粗利率はこれより高くなる。

## なぜ無制限にしないか

Pro を無制限にすると、1店舗が月 3,000 枚生成した時点で原価 ¥39,600 > 売価 ¥29,800 で赤字になる。

- 上限はサーバー側で確認する（画面の表示だけに頼らない）
- 回数と**金額**の両方で止める（モデルを変えたときに回数だけでは守れないため）
- 店舗ごとに上限を変えられる（`organizations.monthly_tryon_limit` / `monthly_cost_limit_jpy`）

## 店舗側の投資対効果（これが売る言葉）

Pro ¥29,800 / 月。オーダースーツ1着の粗利を仮に ¥60,000 とすると、

> **月に1着 多く売れれば元が取れる。**

CORE Suits が1着を増やす経路は3つ。

1. **迷って帰るお客様を減らす**（見て決められる）
2. **単価が上がる**（上位の生地を実際に着た姿で比べられる）
3. **既存のお客様から売上が生まれる**（6ヶ月経過したお客様が自動で並ぶ）

3番目が本命。顧客 300 名の店で、年1回でも再来店が 5% 増えれば 15 着 = 粗利 ¥900,000。

## 計測（ROAI）

「AI を何回使ったか」ではなく「AI がいくらの売上に効いたか」を出す。

```
ROAI = 試着に紐づいたご成約の合計金額 ÷ AI 原価の実測合計
```

- 分子は `purchases.influenced_by_try_on_id` が入っている行**だけ**。推測で広げない
- 分母は `ai_jobs.actual_cost_jpy` の合計（失敗した呼び出しも含む）
- 母数が5名未満のとき成約率は出さない（「0%」と書くと嘘になる）

## 実際の請求と突き合わせる

月初に必ずやる。

1. Google AI Studio / Anthropic Console で前月の請求額（USD）を見る
2. `/analytics` の「AI 原価」と、その月の為替で比較する
3. ずれが 10% を超えたら `src/lib/ai/pricing.ts` の料金表と `SUITS_USD_JPY` を更新する

画面には「各社の公開料金と実測トークン数から計算した推定です。請求額そのものではありません。」と明記してある。
